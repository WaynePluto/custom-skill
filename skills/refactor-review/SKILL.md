# 量化指标驱动的重构

核心规则：**不以 LLM 或人的主观感觉作为重构依据**。是否重构、重构是否完成，都由 `scripts/code_metrics.py` 输出的量化数值决定：首次检测全部达标 → 不重构，直接结束；有不达标项 → 按指标重构 → 复测，直到全部达标。

## 工作流

### 1. 确定范围与阈值

- 扫描目录默认整个项目；脚本自动排除 node_modules、vendor、dist、`__pycache__` 等目录，可用 `--exclude` 追加。
- 默认阈值见 `references/metrics.md`（文件总行数 ≤ 600、函数 ≤ 80 行、圈复杂度 ≤ 15、嵌套 ≤ 4 层、参数 ≤ 5 个、重复率 ≤ 5%、注释全中文且连续注释 ≤ 10 行、循环依赖与未使用 import 为 0 等）。调整阈值必须说明理由并记录，同一项目内保持一致。
- 有关注点分离需求时，用 `--domain-dirs` 指定核心业务目录。

### 2. 基线检测

```powershell
python <本技能目录>/scripts/code_metrics.py <扫描目录> --json <扫描目录>/baseline.json
```

- 退出码 `0`：全部达标。直接报告各项数值即可结束，**不做任何重构**。
- 退出码 `1`：存在不达标项，进入第 3 步。
- 基线 JSON 留作重构后对比，注意提醒用户不要提交到版本控制。

### 3. 按指标重构（仅当有不达标项）

- 每个不达标指标在 `references/metrics.md` 中有对应的"重构手法"，按该节执行；先处理违规数最多的指标。
- 小步进行：每完成一批修改，代码保持可运行、测试可通过。
- 有测试的项目以现有测试为安全网；无测试的项目，第一步先为待重构区域补充特征测试（characterization test）。
- 大型项目拆分文件前，可用 `architecture-map` 技能先生成架构文档辅助定位职责边界。
- 遵守 `references/metrics.md` 的防作弊条款：不许删注释、拆空行、拆行凑数等操纵指标的行为。

### 4. 复测直到达标

```powershell
python <本技能目录>/scripts/code_metrics.py <扫描目录> --compare <扫描目录>/baseline.json
```

`--compare` 输出每项指标"基线 → 当前"的数值变化（改善/恶化/持平），以此衡量重构效果。仍有不达标项则回到第 3 步。

### 5. 交付

- 报告全部指标的 before/after 数值对比，以及"全部达标"的结论。
- 报告较长时写入 `refactor-review-report.md`（项目根目录），回复中给摘要，并提醒该文件不应提交。
- 指标全达标后，仅当用户明确要求更深入审查时，才按 `references/metrics.md` 的"非量化补充信号"人工检查（单实现抽象、混用库、LSP、死代码）；这些信号不作为重构门槛。

## 注意事项

- 指标是门槛不是目标：达标即停止，不为"更好看"的数值继续重构（KISS 同样适用于重构行为本身）。
- 函数级指标与 import 图仅支持 Python；其他语言适用行数、重复率、注释三类门槛，复杂度可用语言工具（radon、ESLint `complexity`）补充但不计入门槛。
- 尊重项目既有惯例：项目统一采用的非典型命名或结构，一致性优先于教科书式正确，用参数适配而不是逐个报违规。
- 清理基线产物：检测产生的 `baseline.json` 与报告文件不属于项目源码，交付时提醒用户删除或加入 `.gitignore`。
