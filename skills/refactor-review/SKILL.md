# 设计原则审查与重构方案

系统性地扫描项目，找出违反设计原则的具体位置，按严重程度排序，产出重构方案。**产出是报告和方案，不直接修改代码**，除非用户明确要求执行重构。

## 工作流

### 1. 了解项目结构

- 若项目根目录存在 `ARCHITECTURE.md`（或 `docs/architecture.md`），先读取它了解模块划分。
- 若不存在且项目规模较大（> 20 个源码文件），建议先运行 `architecture-map` 技能生成架构文档，再继续审查。
- 确认主要语言、目录结构、入口文件。排除生成代码、vendor、node_modules、测试夹具等目录。

### 2. 逐项执行检查

按 `references/checks.md` 中的检查方法逐条执行。该文件为每个原则提供了具体的命令和判断阈值，必须实际运行命令收集证据，不要凭印象下结论。

检查范围可与用户约定：全量审查、指定模块、或仅最近变更（`git diff --name-only <base>`）。默认全量，但大型项目（> 200 个源码文件）先询问用户是否限定范围。

### 3. 汇总与分级

每个发现按以下格式记录：

- **位置**：文件路径与行号（或函数/类名）。
- **违反原则**：具体是哪条，为什么。
- **证据**：命令输出或代码片段（截断到必要长度）。
- **严重度**：
  - **高**：已经造成维护负担（重复逻辑已出现分叉、循环依赖、巨型文件被多人/多轮修改）。
  - **中**：随规模增长会恶化（重复但尚未分叉、职责混杂但改动少）。
  - **低**：风格或一致性问题。

### 4. 产出重构方案

对高、中严重度的问题给出方案，每个方案包含：

1. **目标**：重构后达到的状态（一句话）。
2. **步骤**：可独立验证的小步骤序列，每步保持代码可运行、测试可通过。
3. **风险**：行为变化风险点、需要补充的测试。
4. **成本估计**：涉及的文件数与大致工作量。

方案按"收益/成本"排序，明确建议先做哪几项。不要建议一次性大爆炸式重写。

### 5. 交付

- 发现较少时直接在回复中给出报告。
- 发现较多时写入 `refactor-review-report.md`（项目根目录），回复中给摘要，并提醒用户该文件不应提交到版本控制。

## 注意事项

- 不要把所有"可以更好"的地方都列出来；只报告违反原则且有实际维护代价的问题。KISS 同样适用于重构建议本身。
- 有测试的项目，重构方案必须以现有测试为安全网；无测试的项目，方案第一步应是为待重构区域补充特征测试（characterization test）。
- 尊重项目既有惯例：如果项目统一采用某种非典型模式，一致性优先于教科书式正确。
